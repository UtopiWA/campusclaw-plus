# CampusClaw-Plus 团队项目范围

更新日期：2026-10-31。状态：团队启动阶段的范围草案，供两名成员评审及首轮提交；不表示新增功能已实现，也不替代后续 OpenSpec change 的需求、设计和任务。

## 1. 项目定位与价值

**项目题目：CampusClaw-Plus：基于知识图谱与智能体协作的智能学习诊断与个性化辅导系统。**

在现有 CampusClaw 上继续开发，把材料检索与助手问答扩展为有学习证据支撑的诊断和辅导系统。主要用户为同一教学班的教师与学生，初期围绕数学开展完整演示，数据模型预留学科归属，不在首轮同时铺开全部学科。

学生需要知道“哪里薄弱、为什么、下一步学什么、练习后是否改善”；教师需要知道“本班哪些知识点普遍出错、依据是什么、应如何调整教学”。现有应用提供材料与工具支持的回答，尚未持续保存完整的作答、判题和学习状态，因此不能直接产出可信的掌握度或班级诊断。

本项目的价值在于把**题目、答案、判题、知识点、学习计划和后续练习连接起来**。诊断数值由可解释规则计算，模型负责解释与建议，所有结果能追溯到实际作答和可访问的教学材料。

## 4. 完整扩展目标

以下四项共同构成最终目标。

### 4.1 个人知识图谱与掌握度画像

教师维护知识点及前置/关联关系，题目关联知识点。系统根据学生实际作答与判题结果，按明确、版本化的规则更新知识点掌握度，并保存计算所依据的记录。

学生能查看自己的知识关系、薄弱点及变化；教师能查看本班汇总。没有作答证据时显示“暂无证据”，不把没有数据等同于掌握度为零。图谱初版可由 MySQL 保存节点和关系，无需预先引入图数据库。

### 4.2 AI 个性化学习计划

根据薄弱知识点、前置关系、学生目标、已有任务及可用材料生成学习计划，保存任务顺序、推荐资源和状态。学生完成任务后，新作答进入诊断，系统据此调整未完成任务，保留调整依据与历史，避免覆盖已完成事实。

模型负责组织说明与建议；任务引用的材料和题目必须真实可访问，不能生成不存在的资源。资源不足、模型不可用或计划生成失败须明确显示，不伪造成功计划。

### 4.3 自适应练习与题目推荐

建立包含题型、参考答案、知识点和难度的题库，作业与推荐练习共用题目及作答证据。根据薄弱点、近期表现和可解释规则选择后续题目，保存推荐依据；题目不足时显示实际可用数量，不用重复或无关题目凑数。

学生作答后形成可追溯判题结果，更新错题、掌握度与学习任务。先支持能稳定判定的有限题型，再通过独立 change 扩展主观题或异步 AI 批改；教师复核结果须有明确优先级和历史记录。

### 4.4 班级共性错误分析

教师查看本班按知识点统计的参与人数、作答次数、错误率、薄弱点分布和阶段变化，并能追溯到有权查看的作答证据。页面明确统计时间范围、样本数量和分母，区分未提交与答错。

模型可依据统计和本班材料组织教学建议，但不替代统计计算。学生无权读取同学的个人记录，教师不能跨班查询，演示数据与真实业务统计应可区分。

### 4.5 智能体协作如何落地

题目中的“智能体协作”需要能观察到的职责交接：诊断角色接收学习证据并组织诊断解释；规划角色接收诊断与资源约束并组织计划；辅导角色结合当前任务、题目和材料提供讲解。规则服务负责评分、掌握度和推荐边界，业务编排负责权限、状态与失败处理。

后续 change 必须定义各角色的输入、输出、执行记录与失败传递，并演示一次诊断到规划再到辅导的交接。具体采用现有智能体配置扩展还是受控编排，留待设计评审；当前确定性单技能路由不宣称已具备该协作能力，也不预先要求新增框架或让模型任意选择工具。

## 5. 核心用户链路与第一业务增量

最终演示链路为：

教师维护知识点和题目、布置任务 → 学生提交 → 保存判题与复核结果 → 形成错题和知识点证据 → 更新个人画像 → 生成计划和推荐练习 → 新作答更新诊断与计划 → 教师查看班级共性问题与教学建议。

第一业务增量先实现这条链路的上游：**教师布置有限题型任务 → 本班学生提交 → 系统形成可追溯判题结果 → 教师查看或复核**。该增量是可独立验收的起点，不是整个项目的完成标准。

1. 使用已提交地址的团队仓库，教师可访问，明确唯一主干及保护规则；两名成员各自克隆并按 README 启动。
2. 建立一份团队基线 change，包含 proposal、design、能力 specs 和 tasks，严格校验通过。每项能力有可执行场景，按课件覆盖至少四条相关失败路径及边界；不适用类别写明理由。

现有 `/health` 仅检查数据库并返回状态，尚未满足上述完整健康响应；统一 JSON/request ID 日志及统一检查入口也需在团队基线 change 中确认和补齐。继承已有应用可作为骨架，但不能将个人验收当成团队复现或本课全部要求已完成。

## 8. 安全、失败与实现边界

- 学生只访问自己的学习记录；教师只管理本班资源和分析。逐资源授权在服务端执行，跨班资源保持既有不可访问语义。
- 作答、判题、教师复核及计划变更保留可追溯关系；重复提交、并发复核和任务重试的幂等策略由各 change 明确定义。
- 评分、掌握度和统计采用确定性规则；模型输出是待校验的建议，不能自行覆盖教师复核或虚构学生证据。
- 没有知识点标签、证据不足、题库不足、材料不命中、模型/工具不可用时，返回明确状态；保留已提交事实，不把局部故障伪装为成功。
- 保留当前材料采信、纯工具回答和不可信结果过滤边界。知识推荐不得绕过班级权限，材料引用需指向真实可访问内容。
- 数据迁移沿用 Flyway 只增不改，保持旧材料、配置与会话可读。数据库迁移回退与应用标签回滚分开设计。

范围明确排除：首轮全学科覆盖、完整复刻所有演示页面、SSO/多校多租户、生产级高可用、任意工具自主调用和无边界多智能体系统。关怀式对话、技能 ZIP 包和额外工具示例不自动加入核心承诺；图数据库和新 Agent 框架没有明确需要时不引入。

公网部署与可复现演示属于最终目标；凭据和真实个人学习数据不得进入公开仓库。动态班级管理、更多题型和完整全站审计可按需求追加 change，不将其作为已实现功能。

## 9. 最终验收依据

最终验收至少能展示：真实作答产生知识点证据；画像与薄弱点可解释；计划和推荐引用真实资源；新作答推动状态变化；教师统计与底层记录一致；诊断、规划、辅导角色有可观察交接。

同时覆盖未认证、本人越权、跨班、非法输入、重复操作、资源不足和外部依赖失败等相关路径。自动化测试、接口验收、实际页面及必要的执行记录共同证明完成情况，模型回答看似合理不能单独作为验收通过依据。

团队基线及每个新增能力均通过独立 OpenSpec change 明确验收场景；本文提供全局范围和依赖，不代替具体接口、计算公式、状态机与失败契约。现有行为仍以主规格为准，尚未实现的规划不提前写成当前能力。
