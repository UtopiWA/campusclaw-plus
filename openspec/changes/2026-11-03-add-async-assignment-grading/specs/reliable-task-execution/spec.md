## Purpose

用独立消息代理、事务性发件箱和可独立启停的消费者执行耗时任务，使提交请求快速返回、任务可查询、消息可恢复、结果不重复生效，并让队列、重试、死信和执行耗时能够关联到具体任务。

## ADDED Requirements

### Requirement: 提交解耦与事务性入队

受理接口 MUST 在同一个本地数据库事务中保存业务记录、任务记录和待投递记录，然后返回 HTTP 202 和任务标识；响应 MUST NOT 包含最终结果，受理线程 MUST NOT 调用模型或等待执行完成。事务失败时 MUST 回滚全部业务、任务和发件箱记录；消息代理暂时不可用 MUST NOT 把已提交的业务伪装成失败或丢弃待投递记录。

#### Scenario: 受理请求不等待执行
- **WHEN** 客户端提交一个需要批改的合法请求
- **THEN** 系统 MUST 返回 HTTP 202 和任务标识，MUST NOT 在响应中返回分数或最终结果
- **AND** 受理完成前 MUST NOT 调用模型，业务、任务和发件箱 MUST 同时存在

#### Scenario: 事务失败不留半套数据
- **WHEN** 保存业务、任务或发件箱在事务中失败
- **THEN** 系统 MUST 回滚整个事务，不留下成功提交或孤立任务
- **AND** 客户端 MUST 收到失败响应，且不得出现只有业务记录没有执行凭据的状态

#### Scenario: 代理不可用时仍可靠受理
- **WHEN** 数据库可用但消息代理暂时不可达，客户端提交合法请求
- **THEN** 系统 MUST 保存业务、任务和发件箱并按契约返回 202
- **AND** 待投递记录 MUST 保持可补投，MUST NOT 被标记为已投递或丢失

### Requirement: 可靠发件箱投递

投递器 MUST 读取未完成投递的持久化记录，在数据库事务之外发布到消息代理，并使用发布确认记录投递进度。发布失败 MUST 保留记录并按退避重试；发布成功但尚未标记进度时退出 MUST 允许再次发布，由消费端去重；系统 MUST NOT 把“调用了一次发送方法”当作可靠入队。

#### Scenario: 代理恢复后补投
- **WHEN** 代理不可用期间积累了待投递记录，随后代理恢复
- **THEN** 投递器 MUST 自动补投，任务 MUST 最终被消费者处理
- **AND** 记录 MUST 在确认发布后标记完成，不得凭空标记成功

#### Scenario: 发布后标记前退出
- **WHEN** 投递器已发布消息但尚未记录成功就退出，恢复后再次投递同一任务
- **THEN** 系统 MUST 允许重复投递
- **AND** 消费端 MUST 通过认领和唯一约束保证结果不重复生效

#### Scenario: 投递失败可观察
- **WHEN** 发布持续失败
- **THEN** 发件箱 MUST 保留尝试次数和安全错误码，并按配置退避重试
- **AND** 日志 MUST NOT 包含消息正文、作答、提示词、密钥或供应商原始异常

#### Scenario: 消息被退回不能标记已投递
- **WHEN** 代理确认接收但消息因无匹配路由被退回
- **THEN** 发件箱 MUST 保留可补投状态，不得仅凭 ACK 标记为已投递

### Requirement: 独立可启停消费者

消费者 MUST 作为可独立启动和停止的进程/服务运行，MUST NOT 依赖 Web 请求线程或进程内 `@Async` 完成批改。停止消费者时 Web、数据库、消息代理和投递器 MUST 继续工作；已提交任务 MUST 保留为待处理并可在消费者恢复后自动完成，客户端 MUST NOT 需要重新提交。

#### Scenario: 停消费者不丢任务
- **WHEN** 仅停止消费者，保持 Web、数据库、代理和投递器可用，客户端提交合法请求
- **THEN** 请求 MUST 返回 202，任务状态 MUST 可查询为 `PENDING`
- **AND** 任务/消息 MUST 保留，不得因消费者停止而丢失或伪报成功

#### Scenario: 恢复消费者自动完成
- **WHEN** 消费者重新启动且代理、数据库和模型可用
- **THEN** 待处理任务 MUST 被消费并最终进入 `SUCCEEDED` 或安全 `FAILED`
- **AND** 客户端 MUST NOT 需要重新提交，状态查询 MUST 反映最终结果

#### Scenario: 消费者不提供业务写入口
- **WHEN** 检查消费者进程的对外接口
- **THEN** 消费者 MUST NOT 提供绕过鉴权和班级边界的提交/查询写接口
- **AND** 业务查询 MUST 仍由受鉴权的 Web 接口提供

### Requirement: 至少一次投递与结果幂等

系统 MUST 采用至少一次投递语义，允许消息重复，但业务结果 MUST 只生效一次。数据库 MUST 对结果使用唯一约束，并在同一事务中协调结果和终态；消费者 MUST 在结果提交后 ACK，重复消息 MUST 识别已有结果并安全确认，不得覆盖结果或产生第二份生效结果。系统 MUST NOT 宣称端到端 exactly-once。

#### Scenario: 重复消息只产生一份结果
- **WHEN** 同一任务消息被重复投递或消费者收到重投消息
- **THEN** 数据库 MUST 只有一份生效结果，原分数、判断和时间戳 MUST NOT 被覆盖
- **AND** 重复处理 MUST 可观察，但不得重复计费式调用模型或重复生效

#### Scenario: 结果提交后 ACK 前退出
- **WHEN** 结果和终态已提交，但消费者在 ACK 前退出，消息随后重投
- **THEN** 重投处理 MUST 识别已有结果并安全 ACK
- **AND** 系统 MUST NOT 再次生成结果或把任务改回非终态

#### Scenario: 并发认领不写两份结果
- **WHEN** 两个消费者同时收到同一任务消息
- **THEN** 原子认领 MUST 只允许一个消费者进入执行，另一个 MUST 安全结束
- **AND** 唯一约束 MUST 防止任何竞态下出现第二份生效结果

### Requirement: 原子认领与崩溃/超时恢复

消费者 MUST 使用条件更新或等价原子操作认领任务，模型调用 MUST NOT 占用长数据库事务。消费者执行中退出 MUST 留下可恢复的 `RUNNING` 状态；恢复调度 MUST 在超过阈值后将任务重新置为可执行或终止，并遵守最大尝试次数，不得产生永久 `RUNNING` 或无限重试。

#### Scenario: 执行中退出可恢复
- **WHEN** 消费者认领任务后在模型调用期间退出
- **THEN** 恢复调度 MUST 在超时后将任务重新投递或按上限终止
- **AND** 任务 MUST NOT 永久停留在 `RUNNING`，也不得在恢复时跳过最大次数限制

#### Scenario: 模型等待不占长事务
- **WHEN** 消费者调用模型并等待响应
- **THEN** 认领事务 MUST 已结束，模型网络等待期间 MUST NOT 持有数据库行锁或长事务
- **AND** 结果写入 MUST 使用新的短事务

#### Scenario: 超时阈值大于模型读超时
- **WHEN** 模型响应慢但仍在配置的读超时内
- **THEN** 恢复调度 MUST NOT 将仍在执行的 `RUNNING` 任务误回收
- **AND** 阈值与模型超时 MUST 通过配置明确并记录

#### Scenario: 旧执行迟到不能覆盖重新认领
- **WHEN** 一个执行已被回收，新的执行已经认领，旧执行随后返回成功或失败
- **THEN** 系统 MUST 按认领次数核对写回资格，旧执行不得修改新执行状态或结果
- **AND** 最终结果、重试和死信写入 MUST 在短事务内协调，不能把任何数据库异常都当成唯一键冲突成功

### Requirement: 有限重试、指数退避、抖动与死信

系统 MUST 区分临时性可重试失败与不可重试失败。可重试失败 MUST 在有限次数内按指数退避加随机抖动重试；不可重试失败或达到上限 MUST 置为 `FAILED` 并进入死信，保留安全失败码、尝试次数和任务关联。系统 MUST NOT 无上限重试、固定间隔重试或把随机任务 ID 当幂等键。

#### Scenario: 临时失败按退避重试
- **WHEN** 模型超时、429、临时 5xx 或网络抖动发生
- **THEN** 任务 MUST 在未达上限时回到可执行状态，退避时间 MUST 随尝试次数增长并带随机抖动
- **AND** `attempts` MUST 记录实际执行次数，重试成功 MUST 进入 `SUCCEEDED`

#### Scenario: 不可重试失败及时终止
- **WHEN** 输入非法、模型密钥失效、所需能力不可用或评分依据无法匹配
- **THEN** 系统 MUST 终止并进入 `FAILED`/死信，不得盲目重试
- **AND** 失败原因 MUST 是稳定、脱敏、可关联任务的错误类别

#### Scenario: 达到上限进入死信
- **WHEN** 可重试失败次数达到配置上限
- **THEN** 任务 MUST 置为 `FAILED`，死信队列 MUST 可查看对应任务
- **AND** 死亡消息 MUST 只含任务标识和必要元数据，不含作答、提示词、密钥或完整供应商异常

### Requirement: 观测与安全日志

系统 MUST 提供可复核的队列长度、消费耗时、执行/重试次数和死信数量，并能关联到具体任务。任务状态查询 MUST 只读且无副作用；日志、消息和死信 MUST NOT 包含作答正文、提示词、模型完整响应、密码、密钥或内部地址。任务 ID MUST NOT 成为绕过身份和班级授权的凭证。

#### Scenario: 队列与任务可关联
- **WHEN** 操作者查看队列长度、死信数量、任务 `attempts` 和完成日志
- **THEN** 队列/死信数量 MUST 可读取，完成日志 MUST 含任务标识、状态、尝试次数和耗时
- **AND** 观测 MUST 能区分队列积压、消费变慢和死信，不把单一队列增长直接判为代理故障

#### Scenario: 状态查询无副作用
- **WHEN** 客户端、监控或前端重复查询任务状态
- **THEN** 查询 MUST NOT 触发执行、增加 `attempts`、创建任务或重新投递消息
- **AND** 未登录、非本人或跨班查询 MUST 按既有 401/404 契约拒绝

#### Scenario: 日志和消息不含敏感内容
- **WHEN** 检查结构化日志、队列消息和死信内容
- **THEN** 内容 MUST NOT 包含作答正文、提示词、模型完整响应、数据库/模型/代理凭据或内部地址
- **AND** 敏感字段和换行 MUST 经过安全转义，不得破坏日志结构

### Requirement: 配置、持久化与兼容

消息代理、重试参数、队列名和消费者并发 MUST 通过外部配置注入并写入样例说明；队列、消息和必要数据 MUST 持久化，代理重启后未确认消息 MUST 仍可消费。新增迁移 MUST 只增不改并验证空库与上一版本升级；旧应用在新表存在时 MUST 可继续运行。本能力 MUST NOT 改变现有登录、材料、检索、会话、MCP 和 SSE 契约，也不得把需要立即返回的路径改为排队。

#### Scenario: 代理重启消息仍可消费
- **WHEN** 消息代理重启且存在未确认消息
- **THEN** 持久化队列 MUST 保留消息并在消费者恢复后继续投递
- **AND** 已终态结果 MUST 不因重启重复生效

#### Scenario: 空库和上一版本升级
- **WHEN** 在空库和 V7 数据库上执行 V8 迁移
- **THEN** 迁移 MUST 成功且不修改已交付迁移
- **AND** 旧数据 MUST 可读，旧应用在新表存在时 MUST 按原行为运行

#### Scenario: 既有交互不被全站异步化
- **WHEN** 用户登录、查看材料、检索或使用助手对话
- **THEN** 这些需要立即结果的路径 MUST 保持原有同步语义和 HTTP/SSE 契约
- **AND** 本能力 MUST NOT 宣称端到端 exactly-once
