# 建立团队开发与运行基线

## Why

团队已接入现有 CampusClaw，需要统一运行可观测性、工程规范和检查入口，为后续业务扩展提供共同基线。实现与验证已完成；按项目负责人最新决定，由另一成员独立启动并复现已实现功能、审核后归档提交，不追加复杂实验。

## What Changes

本轮交付能力编号：C1 为部署与健康检查，C2 为请求可观测性，C3 为团队规范、统一检查与可复现交付；对应三份 specs，场景映射见 design。

- 明确成员 A/B 按完整模块负责、另一成员评审验证的分工，修正范围文档中的细碎交叉分配。
- 为后续规范编写确定交付范围：产品、后端、安全、测试、部署运维五类文件，接入 `AGENTS.md` 与必要技能；本次提案不提前生成这些规范。
- 扩展匿名 `GET /health`，保留既有状态值，增加版本、UTC 时间及明确的依赖状态；数据库与 Qdrant 决定就绪，模型与动态 MCP 服务不在探测时执行生成或工具操作。
- 增加后端单行 JSON 日志、请求 ID、异步上下文与脱敏请求完成记录，保持 HTTP/JSON 和 SSE 业务契约。
- 提供一个明确的团队检查入口，复用 Maven、Vitest、Python MCP 与现有接口回归；按环境区分自动检查和真实应用验收，失败不得以跳过伪装通过。
- 按课程要求整理只含配置键名的 `.env.example`，五类规范补齐具体测评判据；秘密只保存在私有环境配置，不进入历史、镜像、前端或日志。
- 保留已通过的运行与测试结果，由另一成员独立启动并复现现有功能，审核代码、规范、配置、结果和本次差异中的敏感信息；在 `docs/lesson-07/README.md` 记录结论，通过后由审核成员同步规格、归档并提交。不追加规范破坏实验、回滚演练或全历史/镜像扫描。

放弃方案：只提交规范、不补运行与验收缺口。该方式无法证明规范生效、独立复现和回滚，不满足团队基线的完成条件。也不清空已有业务以重建空骨架，避免丢失已验收能力与历史。

## Capabilities

### New Capabilities

- `team-development-baseline`：规范可读取、模块分工、统一检查及成员独立复现、审核交付。
- `request-observability`：后端 JSON 日志、可信请求 ID、异步传播、失败记录与敏感内容排除。

### Modified Capabilities

- `auth-upload`：扩展既有“Docker Compose 部署与健康检查”要求的健康响应、依赖就绪与故障契约；保留启动方式和持久化保证。

## Impact

- 运行侧涉及 `HealthController`、健康探测服务/适配器、日志过滤器及配置、`AsyncConfig`、构建版本元数据、Dockerfile 和 Compose 健康超时。
- 工程侧涉及 `docs/project-scope.md`、`docs/project-status.md`、课程总验收记录、`.env.example`、五类规范、`AGENTS.md`、必要技能、统一检查脚本与 README 的简短入口。
- 健康响应新增字段，保留 `status=ok|unhealthy` 和现有 HTTP 成败语义；请求 ID 只新增响应头，不改成功 DTO、`{error}` 或 SSE 事件结构。
- 不新增数据库表、Flyway 迁移或业务路由；不改变班级授权、材料、RAG、技能路由与 MCP 调用行为。复用现有依赖，新增依赖需证明必要性并评审。
- 本次仅简化交付流程，不改变已实现运行行为；归档与提交由另一成员审核通过后执行，标签可选。

## Non-goals

- 不实现作业、错题、知识图谱、学习计划、推荐、班级分析或智能体角色协作。
- 不升级框架、不引入 Actuator/指标平台或分布式追踪系统，不批量迁移 API 路径与响应外壳。
- 不扫描所有教师登记的 MCP 服务，不向模型发送收费生成请求来判断健康。
- 不重写历史迁移或个人归档，不复制真实凭据、成员本机路径或原始请求/响应日志进公开文档。
- 不在此规划轮执行代码实现、规范有效性试验、服务部署、成员复现或版本发布。
