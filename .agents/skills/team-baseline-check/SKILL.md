# 团队基线检查与交付准备

## 输入与定位

输入为仓库位置、change 名和本次范围：只读评审、执行选定检查或整理已实际发生的交付证据。缺省先只读评审，不把“检查一下”解释为部署、收费模型验收、提交或标签发布。

从本 Skill 目录的 `../../..` 定位仓库，确认存在 `AGENTS.md`、`docs/project-status.md` 和 `openspec/`。仓库移动后仍按相对位置解析，不依赖成员绝对路径；结构不匹配先报告，不能在错误目录初始化项目。

## 读取依据

先读 [项目规则](../../../AGENTS.md)、[项目状态](../../../docs/project-status.md)、[范围与模块责任](../../../docs/project-scope.md)，再读选定 change 的 proposal、design、specs 与 tasks。以实际文件为准，不能把四类文档齐全当成实现完成。

按检查对象读取规范：

- 页面/交互：[产品规范](../../../docs/standards/01-product.md)。
- 服务/数据：[后端规范](../../../docs/standards/02-backend.md)。
- 所有评审：[安全规范](../../../docs/standards/03-security.md) 与 [测试/评审规范](../../../docs/standards/04-testing.md)。
- 配置、日志、启动、回滚、最终交付：[运维规范](../../../docs/standards/05-operations.md)。

需要变更规约时采用已有 OpenSpec 流程；本技能不代替提案或 Apply，也不自行批准兼容例外。

## 执行与停止条件

1. 列清本次选定范围、实际存在的入口和环境。`scripts/check.py` 若尚未实现，明确报告，不能运行虚构入口或因此开始实现脚本；已有命令见测试规范。
2. 只读检查文件/场景/任务对应、整模块负责人、规则可达性、继承差异与隐私。分别列出文档已写、评审待做、代码未实现和运行未验证。
3. 已授权运行时按环境选择 unit、integration、api 或 all；先核对依赖，保留原测试隔离和报告位置。Docker/应用不可达、非零退出或跳过不改写为通过，不自动改用真实数据库、开种子或全局装工具。
4. 新会话和另一成员跨机器复现由实际操作者提供证据。没有独立会话就报告未验证，不能把本次对话自检命名为“独立评审”。合规/违规试验在隔离副本中执行且撤去试验补丁；没有授权不制造漏洞或停服务。
5. 回滚只按经核对的运维流程在专用项目/卷执行。目标不隔离、版本缺失或失败就停止该项，不清理真实数据、不改历史迁移；不会因 Skill 被调用就自动获准部署、推送、归档或打标签。
6. 最终核查 change design 的仓库、规约、规范、骨架、交付五维；首次提交含代码不作为缺陷。只有全部所需证据齐备才建议归档/发布，实际操作另按用户授权及对应流程执行。

## 产出

简要报告检查范围、已执行命令及结果、未执行项和原因、阻断项、完整模块负责人和下一步。不得输出秘密、私有地址或个人数据。

实际 Class07 验收证据只汇总到仓库 `docs/lesson-07/README.md`，项目状态只保留摘要和链接；没有真实记录时不创建空目录、不写两名成员已签字。未经实际验证不勾选 tasks，不把历史报告冒充本轮运行结果。
