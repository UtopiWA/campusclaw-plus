# 团队基线检查与交付准备

## 输入与定位

输入为仓库位置、change 名和本次范围：只读评审、执行选定检查或整理已实际发生的交付证据。缺省先只读评审，不把“检查一下”解释为部署、收费模型验收、提交或标签发布。

从本 Skill 目录的 `../../..` 定位仓库，确认存在 `AGENTS.md`、`docs/project-status.md` 和 `openspec/`。仓库移动后仍按相对位置解析，不依赖成员绝对路径；结构不匹配先报告，不能在错误目录初始化项目。

## 读取依据

先读 [项目规则](../../../AGENTS.md)、[项目状态](../../../docs/project-status.md)、[范围与模块责任](../../../docs/project-scope.md)，再读选定 change 的 proposal、design、specs 与 tasks。以实际文件为准，不能把四类文档齐全当成实现完成。

按检查对象读取规范：

- 页面/交互：[产品规范](../../../docs/standards/01-product.md)。
- 服务/数据：[后端规范](../../../docs/standards/02-backend.md)。
- 所有评审：[安全规范](../../../docs/standards/03-security.md) 与 [测试/评审规范](../../../docs/standards/04-testing.md)。
- 配置、日志、启动、回滚、最终交付：[运维规范](../../../docs/standards/05-operations.md)。

需要变更规约时采用已有 OpenSpec 流程；本技能不代替提案或 Apply，也不自行批准兼容例外。

## 审核与收尾

1. 按对应 change 确定本轮范围，不把以往课程或其他 change 的额外实验自动加成门槛。
2. 核对实现、规约、规范、配置说明、已有测试结果和本次差异中的敏感信息。发起方已确认的自动检查可复用；另一成员仍须在自己的环境独立启动，按本轮功能清单实际操作，记录提交、环境类别和结果。
3. 有具体问题时指出文件、影响和修正要求，修改后只补跑受影响检查；没有问题就记录审核通过，不另设新会话、破坏性实验、回滚或全量历史扫描。
4. 另一成员的结论必须真实记录，不由实现者或代理代签。取消的验证不写成通过，失败和缺证据仍如实报告。
5. 独立复现与审核均通过后，由负责收尾的成员按已有 OpenSpec 流程同步主规格、严格校验、归档并提交。提交/推送仍按操作者授权和仓库协作方式执行，标签可选。

## 产出

只输出审核结论、必要问题和下一步，不新增检查台账。当前基线结论维护在 `docs/lesson-07/README.md`，项目状态保留摘要和链接；后续 change 按其约定记录位置执行。
